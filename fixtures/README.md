# Synthetic test fixtures

Every file under `fixtures/` is synthetic project-owned test data. No fixture was copied from a user, production system, credential dump, document corpus, or third-party dataset. The fixtures are covered by the repository's MIT license.

## Provenance policy

- `media/` is generated by `scripts/generate_fixtures.swift` using only literal synthetic strings and system drawing/PDF APIs. Committed bytes are canonical; CI verifies their SHA-256 values and never regenerates them.
- Issue #11 PDF fixtures can be regenerated without touching earlier canonical media by running `swift scripts/generate_fixtures.swift --issue-11`; they cover encrypted, blank, sparse-text, 26-page over-limit, and 20-page mixed documents.
- `contracts/` contains the canonical fake UUID and fake-content V1 contract payloads encoded independently by TypeScript, Swift, and Kotlin tests.
- `corpus/` is hand-authored for this repository. Reserved domains, documentation IP ranges, test phone/card values, and explicit `FAKE` markers prevent examples from being mistaken for live data.
- `governance/` contains synthetic structured-policy invariants and descriptive-prose cases. It does not contain copied issue text or executable policy.
- `malformed/` contains intentionally invalid, truncated, traversal, or breaking-version inputs. These files must never be opened outside isolated test code or uploaded as user artifacts.
- `provenance.json` is the complete machine-checked inventory. Any added, removed, or modified fixture requires an intentional provenance and hash update.

CI may upload only synthetic test reports, lint reports, and unsigned debug build products. Artifact retention is seven days; fixture or report uploads must never include imported device/user data, absolute provider paths, credentials, or signing material.

## Adding a fixture

1. Create it from literals or a checked-in deterministic generator; do not anonymize real user material.
2. Add an inventory entry with purpose, generator/source, license, and SHA-256.
3. Add a test that consumes the fixture and proves its expected positive or negative behavior.
4. Run `npm run test:fixtures` and the platform checks that consume it.
