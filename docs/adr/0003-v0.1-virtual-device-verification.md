# ADR-0003: Virtual-device verification for v0.1

- Status: Accepted
- Date: 2026-08-05
- Decision owner: repository owner
- Scope: AI Context Pack v0.1 only
- Owner record: [Epic #2 decision](https://github.com/phead198708/ai-context-pack/issues/2#issuecomment-5188083764)

## Context

The original v0.1 plan required physical iOS and Android evidence for selected ingestion, performance, accessibility, beta, and release scenarios. The owner selected virtual-only verification for v0.1 and removed that acceptance requirement from the whole scope rather than deferring it to Phase 3.

The change must remain auditable without relabeling virtual-device results as hardware evidence or weakening the functional, privacy, integrity, accessibility, beta, store, and review gates.

## Decision

AI Context Pack v0.1 uses a virtual-device verification policy:

- iOS functional and UI acceptance runs on named iOS Simulator runtimes, including the minimum supported and current runtime available to the pinned Xcode toolchain.
- Android functional and UI acceptance runs on named Emulator/AVD profiles covering API 24, API 35, and compile/target API 36 behavior where an API 36 system image is available.
- Shared tests, XCTest, JUnit/instrumentation, contract fixtures, CI builds, privacy/security audits, and reproducible release artifacts remain authoritative evidence.
- System-share host flows use host applications available in the named Simulator/Emulator image. Missing host applications or virtual OS integrations are documented as limitations rather than treated as passes.
- VoiceOver, TalkBack, Dynamic Type/font scaling, localization, airplane mode, lifecycle, interruption, low-memory, low-disk, and install/upgrade/delete paths use virtual-device controls or deterministic test injection when supported.
- TestFlight and Google Play Internal requirements cover signing, upload, processing, metadata, policy, and track readiness. A physical TestFlight or Play installation is not required.
- At least 20 real beta tasks still cover both iOS and Android with completion rate at least 80%; the people and tasks are real, while execution may use Simulator/Emulator.
- `test:device-required` is not applied to Epic #2 or Issues #3–#24. The label remains available for post-v0.1 or future work that explicitly requires physical hardware.

The versioned repository manifest at `governance/v01-verification-policy.json` and validated GitHub labels are the machine-executable sources for this boundary. Free-form issue prose is descriptive, not the machine-executable source of verification policy. If prose conflicts with the structured policy, maintainers correct the prose through review; an open-ended natural-language parser must not infer or change the release gate.

## Evidence rules

Every virtual-device report records, as applicable:

- Simulator runtime or Android API level and AVD profile;
- Xcode/Android toolchain and host environment;
- build configuration and artifact identifier;
- exact automated command or reproducible manual procedure;
- successful, failed, skipped, and retained item counts;
- timing and resource measurements with the virtual environment identified;
- unavailable host apps, sensors, thermal signals, store-install behavior, or OS integrations.

Virtual results must never be described as physical-device evidence or as proof of hardware performance, thermal behavior, sensor behavior, battery use, camera behavior, or compatibility. An unavailable scenario remains an explicit limitation requiring a release-risk decision; it is never silently omitted.

## Regression enforcement

`npm run test:v01-verification-policy` verifies the pinned SHA-256 integrity and Draft 2020-12 schema of the canonical structured manifest, then runs synthetic manifest, inventory, diagnostic, input-bound, determinism, and prose-invariance tests. `npm run test:workflows` includes this check in the existing Contracts & privacy CI job without granting workflow access to issue metadata or network access to the verifier.

For the live GitHub acceptance boundary, pipe the read-only output of `gh api 'repos/phead198708/ai-context-pack/issues?state=all&per_page=100'` to `node scripts/verify-v01-virtual-verification-policy.mjs --issues-stdin`. The REST response is a transport envelope; the verifier deterministically projects record numbers 2–24 and fails closed unless that inventory is exactly Epic #2 plus Issues #3–#24 with valid, non-empty title/body metadata and valid labels. Missing, duplicate, malformed, type-invalid, or in-range pull-request records fail. Any `test:device-required` label fails under GitHub's case-insensitive label identity. Records outside the v0.1 number range do not enter the inventory, and title/body wording does not change the structured policy result.

## Retained release gates

This decision does not waive:

- image, PDF, text, and URL system sharing and main-app import on both platforms;
- OCR, extraction, recovery, compression, privacy review, irreversible redaction, and export integrity;
- English, Simplified Chinese, VoiceOver, TalkBack, font scaling, and airplane-mode requirements;
- clean iOS app, Share Extension, and Android release builds;
- App Store Connect/TestFlight and Google Play upload, processing, signing, metadata, privacy, policy, and submission readiness;
- 20 real beta tasks, both-platform coverage, and the 80% completion threshold;
- zero open P0/P1 defects, independent PR review, phase approval, or final owner acceptance.

## Consequences

The project can complete v0.1 without external physical hardware. Verification is reproducible on pinned virtual profiles and CI, but it cannot claim measured real-world battery, thermal, camera, sensor, OEM, or hardware-performance behavior. Those limitations must be visible in release evidence and known risks. Physical-device validation may be proposed for a later version, but it is not a hidden v0.1 gate and Issues #25–#27 remain out of scope.
