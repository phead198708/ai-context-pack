# CI, merge checks, and local equivalents

Issue #6 establishes two least-privilege GitHub Actions workflows. They run on every pull request and on pushes to `main`; neither workflow uses `pull_request_target`, repository secrets, signing credentials, or write permissions.

## Pinned toolchains and caches

- Node `22.13.1` comes from `.nvmrc`; npm `10.9.2` comes from `package.json#packageManager`. Workflows assert both exact versions before install.
- Android uses Eclipse Temurin `17.0.19+10` and the committed Gradle `9.3.1` wrapper. The required Android job first launches the minimum supported API 24 x86_64 AOSP image directly with KVM and snapshots disabled, waits for a completed boot, and verifies the device API. The API 24 package manager cannot reliably accept the large self-contained library test APK through ddmlib's split-install stream, so the runner builds the same instrumentation APK, installs a complete local file with `adb install --no-streaming`, and invokes its configured AndroidX runner fail-closed. It runs the complete suite plus the pre-35 PDF fallback explicitly and saves both results in the uploaded report tree. This avoids both the Gradle Managed Device snapshot-creation timeout and the old split-install timeout while making minimum-version compatibility a real required gate. The job then runs every `androidTest` on the checked-in `ciApi34` and `ciApi35` x86_64 AOSP Gradle Managed Devices: API 34 proves the rendered PDF fallback on the last API before the behavior boundary, while API 35 proves embedded-text detection; all three versions also cover contract parity, Inbox scanner, and handoff durability. The emulator package and all three exact x86_64 images are installed together before any emulator starts, so no test task depends on an in-process SDK download. AGP 8.12 also exposes `testedAbi` in the managed-device DSL without propagating it to generated setup tasks, so the narrowly matched `ciApi34Setup` and `ciApi35Setup` tasks repeat the same x86_64 pin; this prevents AGP 9's announced default from silently changing the CI architecture. Node/npm and Gradle caches are keyed by their lock/build inputs and toolchain selected by the setup actions.
- macOS uses the `macos-26` image with Xcode `26.6`, Ruby `3.4.9`, Bundler `2.6.9`, `Gemfile.lock`, and `ios/Podfile.lock`. Xcode 26.6 is the tested SDK 57 baseline and satisfies ADR 0001's Xcode 26.4+ requirement; Xcode 26.3 fails while compiling `expo-modules-jsi` because its Swift compiler cannot disambiguate the package's `abs(Double)` call. CocoaPods commands preload Ruby's standard `logger` library because ActiveSupport 6.1 expects it while security-patched `concurrent-ruby` no longer loads it transitively. The iOS npm script exports an absolute `BUNDLE_GEMFILE` and puts a checked-in shim first on `PATH`; that shim loads `pod` from the bundle even if Expo's own Bundler probe silently falls back to a global install after changing its child process working directory to `ios/`. CI compares the shim version with the locked version before testing. It caches only CocoaPods downloads, never the generated `ios/Pods` tree: the deployment install must reproduce the committed lock from no Pods, then the job removes that generated tree and builds through the supported `npm run ios` entry point. A second tracked-file diff proves Expo did not silently rewrite the lock or native integration files. The download-cache key includes Xcode/Ruby plus all JavaScript/Ruby/Pod locks; DerivedData is never cached.
- Every third-party action is pinned to a full commit SHA and annotated with the reviewed release version.

## Fixtures and artifacts

`fixtures/README.md` and `fixtures/provenance.json` are authoritative. CI verifies an exact inventory and SHA-256 for every synthetic fixture. Reports, unsigned debug products, and coverage are retained for seven days. CI must never upload Inbox/Application Support content, provider URIs, device captures, signing values, or any fixture derived from a user.

## v0.1 structured verification policy

`governance/v01-verification-policy.json` is the canonical machine-executable v0.1 device-verification policy. Its Draft 2020-12 schema is `schemas/governance/v1/v01-verification-policy-v1.schema.json`; both files have pinned SHA-256 digests in the verifier. The existing development-only Ajv pin validates the manifest. No network, registry metadata, locale, POS model, lexical database, or issue-prose interpretation participates in the policy result.

`npm run test:v01-verification-policy` runs synthetic manifest, integrity, inventory, diagnostic, input-bound, determinism, and prose-invariance tests, then validates the canonical files. The CLI bounds policy files to 64 KiB and stdin to 1 MiB and emits only stable rule IDs plus safe issue-number/field context. Free-form issue prose is descriptive, not the machine-executable source of verification policy. The canonical structured manifest and validated GitHub labels define whether physical-device evidence is a release gate.

For the live audit, pipe the read-only REST transport envelope into `node scripts/verify-v01-virtual-verification-policy.mjs --issues-stdin`. The verifier projects numbers 2–24, requires exactly Epic #2 and Issues #3–#24, validates non-empty title/body fields and labels, rejects in-range pull requests and duplicate/malformed records, and rejects `test:device-required` case-insensitively to match GitHub label identity. Out-of-range REST records do not enter the canonical inventory. Content is never printed.

## Dependency gate

The dependency-review action fails newly introduced high/critical vulnerabilities and denies AGPL/GPL licenses. Every dependency diff must also complete the PR template's New Architecture/Expo compatibility, maintenance, license, privacy/network, binary-size, and platform-impact review. Run Expo Doctor after JavaScript/native dependency changes; do not force dependency fixes across locked React Native/Expo ranges.

`expo` 57.0.11 is the exact maintained SDK 57 runtime/tooling pin from the Expo monorepo under the MIT license. This patch stays on the React Native 0.86 New Architecture baseline and aligns the project with Expo Doctor's current SDK recommendation; its approximately 907 KB unpacked package replaces 57.0.10 rather than adding another runtime. The patch updates Expo CLI, Asset, FileSystem, and Modules Core/Worklets on both native platforms, adds no product permission, analytics, backend, or imported-content network path, and requires clean iOS and Android lock/build verification. `expo-dev-client` remains at its independently published 57.0.10 pin because no 57.0.11 package exists.

### Temporary `image-size` audit exception

The repository owner approved this narrowly scoped risk acceptance on 2026-08-08 after GitHub updated two high-severity advisories for every published `image-size` version through 2.0.2. The exception covers only advisory sources `1138808` / `GHSA-w3rx-r6r6-pgpr` and `1138809` / `GHSA-5p2g-fcmc-qvqq` on the locked `metro@0.84.4 -> image-size@1.2.1` build-tool path. Both advisories can hang the Node event loop while parsing crafted ICNS or JXL/HEIF bytes. Metro analyzes repository build assets; it is not shipped as an imported-content parser, and native iOS/Android ingestion never passes user content to this Node dependency. npm offers no patched `image-size` release and non-deterministically proposes either a breaking React Native downgrade to 0.72.17 or an Expo downgrade to 53.0.27; both are incompatible with the approved RN 0.86 / Expo 57 baseline.

`npm run audit:ci` pipes npm's version-2 JSON report into a bounded, deterministic verifier. The verifier pins both complete advisory identities; the exact `via`, `effects`, `nodes`, range, and directness topology of all 13 propagated high records; the exact incompatible npm 10.9.2 fix metadata accepted for every propagated record; and every corresponding high lock node's path, version, registry source, integrity, MIT license, and relevant dependency edges. It rejects duplicate or alternate Metro paths and checks nested advisory severities before the no-high fast path. It fails closed on any critical finding, unknown high finding, additional advisory, top-level/nested severity inconsistency, graph/schema/metadata drift, direct dependency or runtime effect, compatible fix on any propagated record, malformed/oversized input, or lockfile identity/topology change. The workflow verifier separately requires exactly one unconditional `npm run audit:ci` step with no gate-weakening properties and rejects every raw `npm audit` workflow command. `npm run test:npm-audit-policy` proves the pass and rejection cases; the normal dependency-review action still rejects newly introduced high/critical vulnerabilities and forbidden licenses. The first compatible upstream fix, any runtime exposure, or any pinned graph/advisory/lock change requires removal or fresh explicit review of this exception.

## Intentional-regression proof

Before Phase 0 promotion, record a temporary, uncommitted regression for each platform and prove its required check fails:

1. Shared/contracts/privacy: alter a fixture byte or add `filename` to a safe logger record; `npm run test:fixtures` or the logging tests must fail before any sink is called.
2. Android: make one `PrivacySafeLoggerTest` assertion false; `:context-native:testDebugUnitTest` must fail.
3. iOS: make one `PrivacySafeLoggerTests` assertion false; `swift test --package-path modules/context-native/ios` must fail.

Restore the temporary edit, rerun the clean command, and include both expected-failure and clean-pass results in the PR. Never commit the intentional regression.
